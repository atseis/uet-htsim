# Paper Writing SOP Skill

## 概述

本 Skill 的目标是将基于 `atomic-records` 提取的底层实验数据（`code` / `config` / `result` 卡片），逐步向上推演至**学术论文级别**的写作素材。
工作流严格对应“**论文写作 SOP**”，通过 AI 引导式的多轮对话和结构化卡片产出，帮助用户进行深度思考，防止“实验跑完不知道怎么写”或者“Story 与实验脱节”。

---

## 核心概念与卡片规范

所有涉及到**实验数据、论文素材、探究计划 (Plan)** 的生成卡片和人工编写的文档，**一律强制保存在 `AtomicRecords/` 如下四大结构下**，绝不允许将相关文档散落在仓库的其他目录：
- **`New/` 与 `Processed/` (自底向上层)**: 存放基于具体实验生成的底层卡片（`code`, `config`, `result`, `claim`），及其向上推演拼接而成的中高层素材卡片（`story`, `expplan`, `outline`）。这确保了这三类高层卡片依然具有严格的实验溯源链条——新生成的一律放在 New 文件夹，处理后的放在 Processed 文件夹。
- **`Thoughts/` (自顶向下层)**: 存放人类视角的宏观研究计划（如 `Plan-001`、思路备忘录）。它们是您研究初心的源头，指导底层实验的方向。
- **`References/` (外部知识库)**: 存放外部官方规范（如 UEC Spec）、论文文献或 DeepResearch 调研结果，作为 SOTA 和 Ground Truth 的坐标系参照物。

并且在所有文档中，**一律使用标准的双链引用 `[[卡片名称(无后缀)]]` 互相链接**。严禁使用纯文本提及（如“参加 Res-007”）或文件路径引用（如 `[Res-007](path)`）。

### 0. 现有底层卡片 (回放)
由 `atomic-records` 产生的基石卡片：
- **`#code`**: 实验所使用的代码版本。
- **`#config`**: 实验所使用的配置参数。
- **`#result`**: 图片 + 现象描述。
- **`#claim`**: 基于几个 result 的初步结论提取。

### 1. Story / One-Pager 卡片 (`#story` 或 `#onepager`)
- **命名格式**: `Story-<序号(3位)>-<简述>.md` 或 `OnePager-<序号(3位)>-<简述>.md`
  - 例：`Story-001-以Incast破局微突发.md`
- **目的**: 确立论文的核心叙事逻辑。在这个卡片中，现象、动机和提出的设计被有机地结合在一起。
- **核心章节**:
  - `## Problem Statement (问题设定)`: 当前 SOTA 存在的根本缺陷是什么？
  - `## Key Insight (核心洞察)`: 我们的切入点在哪里？(下沉 20% 还是 升维打击？)
  - `## Proposed Design (提出的设计)`: 我们具体做了什么来解决该缺陷。
  - `## Expected Results (预期结果)`: 这个设计在实验上“应该”呈现出什么优于原本缺陷的指标？

### 2. 实验补充计划卡片 (`#expplan`)
- **命名格式**: `ExpPlan-<关联的Story号>-<补充项>.md`
  - 例：`ExpPlan-001-补充消融实验.md`
- **目的**: 基于 `Story` 中立下的 `Expected Results` flag，反查现有的 `#result`，找出还缺乏的证明材料（Gap）。
- **核心章节**:
  - `## 目的 (Objective)`: 为什么需要补这个实验？(例如：为了证明 Orthogonal Design，或补充 Corner Cases)
  - `## 所需配置 (Requirements)`: 描述需要什么样的 `config` (如需关闭某个模块测试 Ablation)。
  - `## 预期图表 (Expected Plot)`: 期待跑出什么样的图像来作证。

### 3. 图表先行大纲卡片 (`#outline`)
- **命名格式**: `Outline-<序号(3位)>-<所涉方向>.md`
  - 例：`Outline-001-HTSim微突发论文大纲.md`
- **目的**: 将所有经过 Story 验证、且补充完整后的 `#result` 组织成论文的行文脉络。
- **核心章节**:
  - `## Motivation (动机图表)`
  - `## System Architecture (系统架构与机理)` 
  - `## Core Performance (核心性能对比)`
  - `## Deep Dive (深度分析与微末测试)`

## 核心工作流 (The SOP Phases)

Agent 在执行本 Skill 时，**必须通过提问和引导的方式与用户共同完成这 6 个阶段**，切勿急于求成一口气替用户写完。**必须严格区分“我的仿真实现了什么”与“最新研究现状（SOTA）/ 官方规范是什么”！**

### Phase 1: Core Claim 提炼与对齐（Atomic -> Claim）

**触发:** 用户说“我想写一个关于 XX 的点子”、“帮我总结一下这些结果”。
**Agent 动作:**
1. 请用户提供几个感觉最有潜力的 `#result` 卡片名称（或已有的初步 `#claim`）。
2. 读取这些对应的卡片（尤其是实验配置解析与结果解读）。
3. **输出:** 帮用户总结出候选的 **Core Claim（核心主张）**。
4. **问:** “这些 Claim 中，哪个最能代表您这次研究的核心突破点？”

### Phase 2: Ground Truth 锚定与仿真溯源 (Simulation vs. Specification Check) 【极其重要】

**触发:** Core Claim 总结完毕之后。
**Agent 动作:**
1. **灵魂出窍警告**: 立刻停止对“SOTA / 现有协议”的随意开火。必须向用户确立一个核心认知：**“我们在仿真（htsim）里跑出来的缺陷，并不等同于真实世界或协议规范自身的缺陷。它可能是我们代码敲错了。”**
2. **规范查证 (Spec Check) - 强制自动检索**: 
   - Agent 必须主动使用文件检索工具（如 `grep_search`），在项目的官方规范文本库（如 `AtomicRecords/References/UE-Specification-6.11.25.txt`）中搜索相关的关键词（例如 `RTO`, `Trim`, `timeout`）。
   - 向用户或在自我思维中确认：“我们发现的这个 RTO 休眠或者 Sleek 信令风暴现象，在检索到的 Spec 片段中是如何强制规定的？”
   - “在我们的模拟器 (`Code-xxx`) 中，这部分逻辑是否严丝合缝地复现了该要求？”
3. **定位责任主体**:
   - 如果 **Spec 确实这么写，我们也严格这么实现了** => 恭喜，我们抓到了 UEC 协议本身的宏观设计缺陷（论文的核心卖点确立，我们是在帮 UEC 协议打补丁！）。
   - 如果 **Spec 没这么写，是我们自己瞎写的** => 立刻打回重练，要求用户去修模拟器的 Bug，不要写论文，卡片作废。
   - 如果 **Spec 语焉不详，导致不同厂商实现可能有歧义** => 这是另一个极佳的故事切入点（探讨协议实现的模糊性代价）。
4. **输出:** 生成结论，并明确标注在接下来的 Story 中。

### Phase 3: 坐标系锚定与查重 (Story Angle Positioning)

**触发:** Ground Truth 责任主体确认无误（确实是协议层面的坑）后。
**Agent 动作:**
1. 引导用户进行灵魂拷问，确立领域的坐标系：
   - “除了 UEC 之外，目前的 SOTA (State of the Art) 有哪些？这个 Claim（协议缺陷点）是否已经被别人做过了？”
2. **智能调研委托 (References Request) 与人机协同分配 【核心工作流】**: 
   - 如果 Agent 存在 SOTA 知识盲区，**绝对不可主观臆断或捏造**。
   - Agent 必须**主动停下来**发起委托，要求用户利用 DeepResearch 检索文献。
   - **分级处理原则**：
     - **宏观横评与次要文献**：指导用户直接使用 NotebookLM 等线上 AI 工具进行交叉提问和总结，只需将**总结报告文本或核心摘要**扔给 Agent。
     - **极度撞车的"假想敌" (Critical Papers)**：一旦 Agent 在阅读总结后锁定 1-3 篇核心竞争对手（例如在唤醒机制上极度相似），Agent 必须**强制明确要求用户去下载这几篇原始 PDF**，存入 `AtomicRecords/References/Raw/`。随后 Agent 会自主调用本地工具深挖这些 PDF 的底层公式与微观设计。
3. **基于调研结果的 Angle 调整：**
   - **如果已经被做过（或者有高度相似的工作）：** 启发用户寻找新切入点（**缩小靶心**关注极端长尾，或**升维打击**提炼通用架构准则）。
   - **如果没有被做过：** 启发用户精确定位“增量”，明确本工作的“立足点”与意义（例如：我们是**基于 UEC 规范**提出的改进架构）。

### Phase 4: 确定故事与撰写 One-Pager (Storytelling)

**触发:** 坐标系与角度 (Angle) 已经明确。
**Agent 动作:**
1. 引导用户重构 Motivation（动机），从头捋顺因果逻辑，并**必须在行文中清晰界定什么是“基于 UEC Spec 的观察”**。
2. 帮用户起草一份 **One-Pager（一页纸提案）**，并将结果保存为 `#story` 卡片中。
3. 严格遵循 `Problem Statement -> Key Insight -> Proposed Design -> Expected Results` 的逻辑流。
4. **输出:** 提供起草的卡片内容供用户 Review。

### Phase 5: 实验补充查漏补缺 (Gap Analysis & ExpPlan)

**触发:** One-Pager (Story) 确定之后。
**Agent 动作:**
1. **对比审查:** 将 Story 中的 `Expected Results` 与目前所有的 `#result` 进行盘点对比。
2. **灵魂拷问:** “如果评审看到这份 Story，现在的图表足以支撑这个庞大的叙事吗？”
3. 指出可能缺乏的实验维度：
   - **正交实验设计 (Orthogonal Design)**: 你的机制是否和其他机制存在冲突？
   - **消融实验 (Ablation Study)**: 你的设计如果拆分为组件 A 和组件 B，分别的贡献是多少？
   - **极端反例 (Corner Cases)**: 极端负载下，机制会不会反而劣化 (例如 Incast 风暴下)？
4. **输出:** 根据发现的 Gap，协助起草 `#expplan` 卡片，指导用户回到 `atomic-records` 或模拟器代码中去跑补充实验。
   *(此后用户可能会挂起任务去跑实验，等新的 result 卡片生成后，再回来继续。)*

### Phase 6: 故事与实验都立住之后（图表先行与大纲打磨）

**触发:** 所有关键的补救实验都跑完，并且证明了预期的结果（也就是“故事”和“实验”都逻辑自洽了）。
**Agent 动作:**
1. 将散落的成功 `#result` 收集起来，按照论文的自然排版逻辑进行分类。
2. 帮用户起草 **`#outline`** 卡片，排布好“图表先行”的骨架。
3. 提示用户在这份大纲的基础上，结合文献评述、算法逻辑等细节步入真正的 Markdown 原稿编写打磨阶段。

## 执行指南与 Prompt 技巧

1. **红线警戒 (Simulation $\neq$ SOTA 且断言必有依据):** 永远保持清醒，**实验结果只是现象，不等同于全球的 SOTA 必然也有这个缺陷**。在帮用户写东西时，所有对“现有技术 / 传统基线缺陷”的宏观断言，**必须（MUST）** 提供明确的参考文献（例如 `[Roundabout, ICNP'24]` 或 `[Aeolus, SIGCOMM'20]`）。如果没有明确的外部顶会文献背书，这些措辞务必降级、收敛，严格标明：“在模拟 UEC 规范的架构实现中单方面观察到...”，绝不可凭空捏造“当前的最新技术存在...”。
2. **强制校验 Spec:** 不要让用户把自己的 Bug 当成一篇论文去发。必须在 Phase 2 时进行物理隔离和确认，与 `UE-Specification` 文档交叉比对。
3. **绝对不要做越俎代庖的瞎编:** 所有的 Story 必须极其紧密地咬合真实存在的 `#result` 与可查证的 References。绝不能为了圆故事而虚构不曾被证明的“机制优越性”。如果发现机制优越性尚未被证据支撑，立刻退回到 Phase 5 要求跑补充实验。
4. **循循善诱:** 学术写作的难点在于理清思路，Agent 的主要价值是**不断追问那些痛点问题**（“如果你说提升了 20%，那代价是什么？”“这个参数是否在真实场景下也是合理的？”）。
5. **严格追踪卡片双链:** 当你在生成 Story 或 Outline 的文本内容时，一定要把引用的 `#result` 以及 `#claim` 卡片以双链 `[[卡片名]]` 形式严密嵌入。这有助于保持上下文的可溯源性。
